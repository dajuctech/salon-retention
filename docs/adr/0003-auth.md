# ADR-0003: Authentication with Better Auth

- Status: Accepted
- Date: 2026-10-16

## Context
We need staff logins, users who belong to several salons, roles per salon, invitations, and the ability to revoke sessions. v0 listed Auth.js or Clerk.

## Decision
Use **Better Auth** (open source, runs inside our app, stores data in our Postgres through Prisma). Its organization plugin maps to salons (organization = salon, member = staff with a role) and handles invitations.

Customers have **no accounts** in R1. They act through links signed with an HMAC and limited to one booking.

## Alternatives considered
- **Auth.js / NextAuth.** It has no built-in support for organizations, invitations or roles, so we'd have to build them. The project is now maintained by the Better Auth team.
- **Clerk.** Fastest to set up, but cost grows with each user, user data lives with a third party, and it adds vendor lock-in for a price-sensitive market.

## Consequences
- We own the user tables and session security. We must apply security updates.
- MFA (multi-factor authentication) for owners is available through a plugin, planned for R1.1.

## Amendment (2026-10-16): identity only

While building, we chose to use Better Auth **only for identity**: users, passwords, sessions, email sign-in codes and password reset. Salon membership, roles and invitations live in our own `Member` and `Invitation` tables (`src/server/auth/onboarding.ts`) instead of the organization plugin, because:
- the `salon` table has required settings (country, timezone, currency) that the plugin can't create;
- roles must follow our own permission matrix (`src/domain/permissions.ts`), not a second role system;
- invitation tokens are stored only as SHA-256 hashes and are tied to the invited email address.

The active salon for users with several memberships is kept in an httpOnly cookie and always checked against active memberships (`requireStaff()`).
